# cachekeeper

[English](README.md) · **한국어**

**살아 있는 프롬프트 캐시를 실수로 버리지 않게 해 주는 Claude Code 플러그인입니다.** 세 가지로 이루어져 있습니다.

- **모델 전환 가드**: `/model`이나 모델 선택기로 캐시가 살아 있는 세션의 모델을 바꾸려 하면, 잃게 될 양과 캐시를 지키는 대안을 보여 주고 먼저 묻습니다.
- **`cachekeeper audit`**: 내 대화 기록을 읽어 캐시 재구축을 원인별로 나눠, 어떤 습관이 가장 비싼지 보여 줍니다. `cachekeeper keepalive`는 내 경우 keep-alive를 몇 시간까지 켜 두는 게 이득이었을지, `cachekeeper compaction`은 더 일찍 압축했다면 얼마를 아꼈을지 찾아 줍니다.
- 직접 켜는 **keep-alive**: 자리를 비운 동안 55분마다 짧은 요청 하나로 긴 세션의 캐시를 살려 둡니다. 다시 쓰는 것보다 쌀 때까지만입니다.

## 사용법

**1. 설치.** Python 3.8 이상이 필요합니다([요구 사항](#요구-사항과-설정)).

```
claude plugin marketplace add grapefruit0205/cachekeeper
claude plugin install cachekeeper@cachekeeper
```

업데이트는 `claude plugin marketplace update cachekeeper`, `claude plugin update cachekeeper@cachekeeper`를 차례로 실행하고 Claude Code를 다시 시작하면 됩니다. 지우려면 `claude plugin uninstall cachekeeper@cachekeeper`.

**2. 모델 전환 가드는 설정할 게 없습니다.** `/model`이나 모델 선택기로 바꾸면 살아 있는 캐시를 버리게 되고 다시 쓰는 양이 $1 이상일 때, 전환을 멈추고 금액을 보여 줍니다. 그다음은 둘 중 하나입니다.

- 이 작업만 다른 모델로 하려면: 하려던 요청을 그대로 보내세요. 그 모델의 서브에이전트가 처리하고, 세션은 모델과 캐시를 그대로 유지합니다.
- 그래도 세션 모델을 바꾸려면: 안내된 `/model` 명령을 120초 안에 입력하세요(터미널 세션에서는 확인 창이 뜹니다).

**3. keep-alive 켜기 (선택).** `~/.claude/settings.json`에 넣습니다. 이미 `env`가 있으면 그 안에 한 줄만 넣으면 됩니다.

```json
{
  "env": {
    "CACHEKEEPER_KEEPALIVE": "auto"
  }
}
```

그러면 긴 세션에서 턴이 끝날 때마다, 자리를 비운 동안 캐시를 살려 둡니다. 어떤 세션을 몇 시간까지 살릴지는 내 기록으로 계산하고, 하루 한 번 다시 계산합니다. 컴퓨터가 깨어 있고 세션이 열려 있을 때만 동작합니다. `auto` 대신 `1`을 쓰면 고정 설정으로 동작합니다([keep-alive](#keep-alive-직접-켜야-동작)).

**4. 내 사용량 보기.** 세션에서 `/cachekeeper:audit`를 입력하거나, Claude에게 아래 명령을 실행해 달라고 하세요(플러그인이 `cachekeeper`를 Claude Code 셸의 PATH에 넣어 둡니다).

| 명령 | 보여 주는 것 |
|---|---|
| `cachekeeper audit` | 사용량 구성과, 캐시 재구축마다의 원인 |
| `cachekeeper keepalive` | 내 기록에서 이득인 keep-alive 정책과, `auto`가 지금 쓰는 정책 |
| `cachekeeper compaction` | 자동 압축을 더 일찍 했다면 아꼈을 양과 든 비용 |
| `cachekeeper events` | 가드가 물은 전환과 keep-alive 핑 기록 |

`--days N`으로 기간(기본 30일), `--lang ko`나 `--lang en`으로 언어, `--basis subscription`이나 `--basis api`로 [잣대](#두-가지-잣대)를 고릅니다. `audit --json`은 숫자를 JSON으로 출력합니다. 명령은 이 컴퓨터의 대화 기록만 읽고 아무것도 보내지 않습니다. Claude Code 밖의 터미널에서는 저장소를 받아 실행합니다: `git clone https://github.com/grapefruit0205/cachekeeper` 다음 `cachekeeper/bin/cachekeeper audit`.

## 왜 필요한가

Claude Code는 매 턴마다 대화 전체를 다시 보냅니다. 프롬프트 캐시 덕분에 이게 싸게 처리됩니다. 캐시를 다시 만들면 맥락 전체를 다시 씁니다. 각각이 얼마인지는 누가 세느냐에 따라 다릅니다.

- **API 정가**로는 캐시 읽기가 입력 단가의 0.1배 이하, 1시간 캐시 쓰기가 2배입니다.
- **구독 요금제의 사용량 한도**로는, 외부 실측에 따르면 캐시 읽기가 거의 0(입력 단가의 0.18%)이고 쓰기는 입력 단가로 셉니다([두 가지 잣대](#두-가지-잣대)).

만든 사람의 기록 12.7일치(2026-09-11~24, 메인 세션 152개, 요청 9,658개, 그중 94%가 1시간 캐시)는 이렇습니다.

| | 구독 사용량 | API 정가 |
|---|---|---|
| 캐시 읽기 | 4.6% | 54.8% |
| 캐시 쓰기 | 51.0% | 31.5% |
| 출력 | 44.4% | 13.7% |

캐시 쓰기의 원인이 된 재구축은 이렇게 나뉩니다.

| 원인 | 재구축 횟수 | 중간 크기 | 구독 사용량 | API 정가 |
|---|---|---|---|---|
| **모델 전환 (`/model`)** | 35 | 54.5만 토큰 | **12.5%** | 7.7% |
| **1시간 넘게 쉼 (TTL 만료)** | 42 | 45.6만 토큰 | **11.8%** | 7.3% |
| 기타 (도구 정의, 업그레이드, 이미지) | 17 | 63.4만 토큰 | 4.8% | 3.0% |
| 세션 시작·재개 | 18 | 14.7만 토큰 | 4.1% | 2.6% |
| 자동 전환, effort 변경, 압축 | 13 | | 2.3% | 1.4% |

읽기가 거의 공짜인 구독에서는 재구축이 한 턴이 할 수 있는 가장 비싼 일입니다. 가드와 keep-alive가 다루는 두 습관이 만든 사람 사용량의 4분의 1을 차지합니다. 45만 토큰짜리 세션에서 Opus 5와 Fable 5.1 사이를 한 번 오가면 대화 전체를 새 모델에 다시 캐싱합니다(Fable 5.1 기준 구독 사용량으로 약 $4.50, API 정가로 약 $9). API 정가로 잰 첫 측정 기록은 [docs/measurement-2026-09-23.md](docs/measurement-2026-09-23.md)에 있습니다.

## 두 가지 잣대

cachekeeper가 보여 주는 모든 금액(가드의 추정, 감사의 비중, keep-alive와 압축 재현)은 두 잣대 중 하나로 잽니다.

| 잣대 | 캐시 읽기 | 캐시 쓰기 (5분 / 1시간) | 캐시 안 된 입력 | 출력 |
|---|---|---|---|---|
| `subscription` | 입력의 0.0018배 | 입력의 1배 / 1배 | 입력의 1배 | 출력 단가 |
| `api` | 입력의 0.1배 이하 | 입력의 1.25배 / 2배 | 입력의 1배 | 출력 단가 |

`subscription`은 구독 요금제의 사용량 한도가 세는 방식입니다. 공식이 공개되어 있지 않아 외부 실측에 기댑니다. [she-llac.com](https://she-llac.com/claude-limits)이 2026년 1월 반올림되지 않은 사용량 값에서 역산했고(캐시 읽기는 입력 단가의 0.18%로 추정, 80% 구간 0~0.5%. cachekeeper는 이 추정값을 씁니다), alldonesites 사용량 추적(Max 20x 계정 4개, 2026-09-21까지)에서는 Fable 5.1이 Opus 5의 2.11배로 세어져 정가 비율과 비슷했습니다. 1시간 캐시 쓰기도 입력 단가로 센다는 것과 Opus 5.5가 정가에 비례한다는 것은 가정입니다. 이 잣대의 금액은 한도가 세는 토큰을 API 정가 달러로 환산한 값이니, 청구액이 아니라 요금제 사용량의 비중으로 읽어 주세요.

기본값은 캐시를 따릅니다. Claude Code 2.1.280은 사용량 한도 안의 구독에만 메인 대화에 1시간 캐시를 주고, API 키나 추가 사용량(API 요금으로 청구) 상태에서는 5분을 줍니다. 그래서 1시간 캐시 세션은 `subscription`, 5분 캐시 세션은 `api`로 셉니다. API 키로 `ENABLE_PROMPT_CACHING_1H`를 켜서 1시간 캐시를 쓰는 경우처럼 이 연결이 깨지면 `CACHEKEEPER_BASIS=api`(또는 `subscription`)로 고정하세요. 명령마다 `--basis`도 받습니다.

## 모델 전환 가드

전환 비용은 Claude Code가 이미 계산합니다. `PreModelSwitch` hook 입력에 `prompt_cache_warm`, `context_tokens`, `cache_ttl`, `estimated_cache_write_usd`가 들어 있습니다(Claude Code 2.1.280에서 확인). 캐시가 살아 있고 다시 쓰는 금액이 `$1` 이상이면 cachekeeper가 `ask`로 이렇게 답합니다.

```
cachekeeper: opus-5 → fable-5-1로 바꾸면 지금 살아 있는 캐시(1h)를 버리고 대화 452k 토큰을
fable-5-1에 다시 씁니다 — 약 $4.52 (구독 사용량 기준: 캐시 쓰기를 입력 단가로 셈). 이 작업만
fable-5-1로 하시겠습니까? 하려던 요청을 그대로 보내면 fable-5-1 서브에이전트가 처리하고, 끝나면
지금 모델(opus-5)로 이어집니다. 세션 모델 자체를 바꾸려면 120초 안에 `/model claude-fable-5-1`를
입력하세요 (모델 선택기에서 같은 모델을 다시 누르면 전달되지 않을 수 있습니다).
```

1시간 캐시에서는 Claude Code의 추정에서 쓰기 할증(2배)을 뺀 구독 사용량 기준 금액을 보여 줍니다. 5분 캐시이거나 `CACHEKEEPER_BASIS=api`이면 Claude Code의 API 정가 추정(`약 $9.04 (API 정가 기준)`)을 그대로 씁니다. `$1` 기준도 같은 잣대로 재므로, 구독 사용량 기준에서는 Opus 5.5는 약 25만 토큰, Fable 5.1은 약 10만 토큰부터 묻습니다(API 정가로는 12.5만, 5만). 0.6.0 이전만큼 자주 묻게 하려면 `CACHEKEEPER_MIN_USD=0.5`로 두세요.

- 터미널 세션에서는 Claude Code가 이 문구로 확인 창을 띄웁니다.
- **Claude 데스크톱 앱**과 headless `-p` 세션에는 확인 창이 없습니다. 데스크톱 앱에서는 모델 선택기도, 직접 입력한 `/model`도 앱을 거쳐 Claude Code에 전달됩니다. 이때 전환은 이 문구와 함께 막히고, **안내문에 적힌 `/model` 명령을 120초 안에 입력하면 그게 확인입니다.** 2026-09-23 데스크톱 앱에서 확인했습니다. `/model opus`가 안내문과 함께 막혔고, 21초 뒤 같은 명령을 입력하자 세션이 바뀌었습니다.
- 데스크톱 앱의 모델 선택기에서 같은 모델을 다시 눌러 확인하지 마세요. 전환이 막힌 뒤에도 선택기에는 새 모델이 표시된 채 남고 실제 세션은 이전 모델 그대로일 수 있습니다. 이 상태에서 다시 눌러도 아무 요청도 보내지지 않습니다. 선택기 표시와 실제 세션이 다르면, 지금 세션의 모델을 선택기에서 골라 맞춰 주세요.
- 캐시가 이미 식은 전환, 맥락이 작은 전환, 자동 폴백, 세션 재개 때의 모델 복원은 조용히 통과합니다. `PreModelSwitch`는 `/model`, 모델 선택기, SDK 호출에서만 실행됩니다.
- 서브에이전트는 메인 캐시를 건드리지 않습니다. 호출과 결과가 대화 끝에 붙을 뿐이고, 서브에이전트는 자기 모델로 자기 캐시를 따로 만듭니다.

### 이 작업만 다른 모델로

전환을 막을 때 더 싼 방법도 함께 제안합니다. **다른 모델에 맡기려던 요청을 다음 메시지로 그냥 보내면, 그 모델의 서브에이전트가 처리합니다.** 세션은 원래 모델을 유지하고, 캐시도 그대로 살아 있습니다. `UserPromptSubmit` hook이 메인 모델에게 그 메시지 하나를 서브에이전트에 맡기라고 지시합니다(Agent 도구, 요청한 모델 그대로 예: `model: "claude-fable-5-1"`, 안 되면 별칭 `fable`). 방향은 상관없습니다. Fable에서 `/model claude-opus-5`를 치면 Opus 5 서브에이전트를 제안합니다. 서브에이전트는 대화를 보지 못하므로 메인 모델이 필요한 내용을 정리해 넘깁니다. 그다음 메시지부터는 평소대로 처리됩니다. 안내문의 `/model` 명령을 입력하면 기존처럼 세션 모델 자체를 바꿉니다.

2026-09-23에 메인 모델을 Opus 5.5로 두고 실제로 확인했습니다. 전환이 막힌 뒤 다음 요청이 다른 모델의 서브에이전트로 넘어갔고(`Agent`, `model: "sonnet"`), 답 끝에 "This session is still on Opus"가 붙었습니다. 메인 모델이 Haiku 4.5일 때는 지시가 전달되고도 세 번 모두 무시됐습니다. 이 제안은 메인 모델이 지시를 얼마나 잘 따르는지만큼만 믿을 수 있습니다.

모든 전환 요청과 실제 전환은 플러그인 데이터 디렉터리의 `events.jsonl`에 기록됩니다. 모델 이름, 토큰 수, 추정 비용, 결정만 남고 프롬프트 내용은 남지 않습니다. `cachekeeper events`로 요약해 볼 수 있습니다.

## 감사(audit)

```
cachekeeper audit            # 최근 30일(기록이 더 짧으면 있는 만큼), 로케일 언어(ko/en)로
cachekeeper audit --days 7 --json
```

세션 안에서는 `/cachekeeper:audit`로 실행할 수 있습니다. `cachekeeper keepalive`는 쉬는 시간이 어떻게 분포하는지와, 어떤 keep-alive 정책(몇 시간까지 살려 둘지, 어느 크기 이상의 세션만 살려 둘지)이 이득이었을지 보여 줍니다. `~/.claude/projects/*/*.jsonl`(메인 세션만, 서브에이전트 제외)을 읽고, 세션 재개로 다른 파일에 복사된 응답도 한 번만 셉니다. 보고하는 내용은 네 가지입니다.

- 사용량 구성: 캐시 읽기, 캐시 쓰기, 출력, 입력
- 모든 재구축과 그 원인: 세션 시작, 직접 또는 자동 모델 전환, effort 변경, 압축, TTL 만료, 기타
- 가드 재현: 내 전환 중 가드가 물었을 횟수와, 그 답에 걸려 있던 사용량
- 55분 keep-alive 재현: 핑 비용과, 그 핑이 막았을 만료 재구축. 세션의 마지막 메시지 뒤에 나갔을 핑도 돌아왔든 아니든 비용으로 세고, keep-alive가 개입하지 않는 `claude -p` 실행은 뺍니다.

비중은 세션이 쓰는 잣대로 잰 값입니다([두 가지 잣대](#두-가지-잣대)). `--basis subscription`이나 `--basis api`로 고를 수 있습니다.

## 세션을 얼마나 키울 것인가

매 요청이 대화 전체를 다시 읽으므로, API 정가로는 긴 세션이 턴마다 그 길이만큼 값을 치릅니다. 만든 사람 기록에서는 요청당 중간값 40만 토큰을 다시 보냈고, 맥락 중 30만 토큰을 넘는 부분을 다시 읽는 데만 전체 사용량의 24%가 들었습니다. 구독 사용량으로는 다시 읽기가 거의 0이고, 긴 맥락은 쉬었다 오거나 모델을 바꿔 다시 쓸 때 값을 치릅니다. Claude Code는 모델의 창 전체(현재 모델은 100만 토큰)가 거의 찼을 때만 자동으로 압축합니다. 만든 사람 세션은 약 97만 토큰에서 압축됐습니다. `autoCompactWindow` 설정(또는 `CLAUDE_CODE_AUTO_COMPACT_WINDOW`, 10만~100만 토큰)으로 더 일찍 압축하게 할 수 있습니다.

```
cachekeeper compaction       # 더 일찍 압축했다면 얼마를 아끼고 얼마가 들었을지, 내 기록으로
```

모든 세션을 더 작은 창으로 다시 재생합니다. 맥락은 실제와 같은 만큼씩 자라고, 창을 넘으면 압축이 맥락을 읽고 요약을 쓴 뒤 실제 압축들이 남긴 크기에서 이어 갑니다. 만든 사람의 실제 압축 15번에서 잰 값은 이렇습니다. 압축 뒤 대화는 7만 토큰에서 이어졌고, 그중 첫 요청이 새로 쓴 것은 3.5만(시스템 프롬프트와 도구는 캐시에 남음), 요약 출력은 5.3천 토큰, 압축 전에 읽었던 파일을 다시 읽은 양은 1.4만 토큰이었습니다. 괄호 안의 신중한 값은 다시 읽기 4.5만(압축 뒤 늘어난 맥락 전부, 상한)과 요약 1.5만을 가정한 것입니다. 만든 사람의 12.7일치 순효과(신중한 값)입니다.

| 창 | 하루 압축 | 구독 사용량 | API 정가 |
|---|---|---|---|
| 20만 | 16번 | +16% (−3%) | +46% (+36%) |
| 30만 | 9번 | +17% (+10%) | +43% (+38%) |
| 40만 | 5번 | +17% (+12%) | +38% (+34%) |
| 60만 | 4번 | +15% (+11%) | +29% (+27%) |
| 80만 | 2번 | +5% (+3%) | +15% (+13%) |

API 정가로는 절감의 대부분이 줄어든 다시 읽기입니다. 구독 사용량으로는 거의 전부가 쉬었다 오거나 모델을 바꾼 뒤 작아진 재구축에서 압축 자체의 비용을 뺀 값이라, keep-alive의 절감과 겹칩니다. keep-alive가 이어 준 휴식에는 줄일 재구축이 남아 있지 않습니다.

비용만 잰 값입니다. 압축은 요약에서 빠진 세부를 잃게 하고, 창이 작을수록 더 자주 잃습니다. 그게 긴 맥락보다 더 비싼지는 청구서가 아니라 작업의 문제입니다. 작업 단위가 끝났을 때 `/compact`(남길 내용을 적어서)로 직접 압축하는 편이, 창이 우연히 걸린 지점에서 압축되는 것보다 많이 남깁니다. 창은 그걸 놓쳤을 때의 안전망입니다. Claude Code의 `/config` 안내는 비용과 성능 모두를 위해 자동 창을 권합니다. 이 재현은 그와 견줘 볼 내 기록 기준의 숫자입니다.

## keep-alive (직접 켜야 동작)

한 시간 넘게 쉬었다가 돌아오면 대화 전체를 다시 캐시에 씁니다. `CACHEKEEPER_KEEPALIVE=1`을 설정하면, 자리를 비운 동안 긴 세션의 캐시를 살려 둡니다. 다시 쓰는 것보다 쌀 때까지만입니다.

- 턴이 끝나면 `Stop` hook이 백그라운드에서 기다립니다(`asyncRewake` hook: 종료 코드 2로 끝날 때만 Claude Code가 모델을 깨웁니다). 마지막 요청이 시작된 지 55분이 되면 모델을 깨우고, 모델은 `(keep-alive)`라고만 답합니다. 이 요청 하나가 캐시를 읽고 한 시간을 다시 시작합니다. 30만 토큰짜리 Opus 5.5 대화라면 API 정가로 핑 한 번에 약 $0.07(거의 다 읽기), 다시 쓰면 $2.40입니다. 구독 사용량으로는 읽기가 거의 0이라 핑은 주로 자기 토큰 몇백 개만큼인 약 $0.007이고, 다시 쓰면 $1.20입니다(만든 사람의 핑 15번은 평균 511토큰을 쓰고 123토큰으로 답했습니다).
- 1시간 캐시를 쓰는 10만 토큰 이상의 대화만, 연속 최대 3번까지 핑합니다. 그 뒤 캐시가 한 시간 더 살아 있으니 자리를 뜬 뒤 약 3시간 45분까지입니다. 다음 메시지를 보내면 횟수가 처음부터 다시 셉니다.
- 사용자가 입력하거나, 다른 턴이 끝나거나, 모델을 바꾸거나(다음 요청이 어차피 다시 씀), `/compact` 뒤, 컴퓨터가 잠들어 한 시간이 지나 버린 경우에는 물러납니다. `claude -p` 실행에는 개입하지 않습니다.

어떤 숫자가 이득인지는 쉬는 습관과 잣대에 달려 있습니다. `cachekeeper keepalive`가 내 기록(돌아온 휴식, 그리고 핑이 비용만 들었을 각 세션의 마지막 메시지 뒤 시간)을 재현해 가장 좋은 정책과 붙여 넣을 설정을 출력합니다. 만든 사람의 12.7일치에서는:

- 구독 사용량 기준: 10만 토큰 이상인 세션을 최대 24시간 살렸다면 핑 1,981번(사용량의 2.5%)으로 재구축 40번(11.0%)을 막아 순효과 +8.5%. 최대 3시간이면 +7.0%. 읽기를 0으로 치면 24시간이 +10.0%, 구간 상단인 입력 단가의 0.5%로 치면 +6.1%로 3시간(+6.2%)과 비슷합니다.
- API 정가 기준: 30만 토큰 이상인 세션을 최대 2시간 — 핑 161번(1.5%)으로 재구축 20번(3.9%)을 막아 순효과 +2.4%. 최대 24시간이면 −6.9%입니다. 그 한도에서는 핑의 3분의 2가 끝내 돌아오지 않은 세션으로 나가고, API 정가로는 핑마다 대화 전체를 다시 읽기 때문입니다.

재현은 컴퓨터가 계속 깨어 있다고 가정합니다. 핑은 컴퓨터가 깨어 있고 세션이 열려 있을 때만 나가므로, 밤에 잠드는 컴퓨터에서는 잠들기 전까지의 핑만 쓰이고 아침 재구축은 어차피 일어납니다. 구독 사용량으로는 그 핑이 한 번에 1센트도 안 되니, 긴 한도의 위험은 작습니다.

| 변수 | 기본값 | 효과 |
|---|---|---|
| `CACHEKEEPER_KEEPALIVE` | 꺼짐 | `1`: 아래 설정대로 켜짐. `auto`: 내 기록에서 가장 좋은 정책으로 켜짐, 매일 다시 계산 |
| `CACHEKEEPER_KEEPALIVE_MIN_TOKENS` | `100000` | 이보다 작은 대화는 만료되게 둠 |
| `CACHEKEEPER_KEEPALIVE_HOURS` | `3` | 마지막 메시지 뒤 몇 시간까지 핑할지 |
| `CACHEKEEPER_KEEPALIVE_MINUTES` | `55` | 핑 전에 기다리는 분 |

`auto`로 두면 Stop hook이 하루 한 번 백그라운드에서 `cachekeeper keepalive`의 재현을 다시 하고, 가장 좋은 정책으로 기다립니다(이때 위의 두 설정은 무시되고, 차이가 1% 안인 정책끼리는 핑이 적은 쪽을 고릅니다). keep-alive는 1시간 캐시 세션에서만 기다리므로 재현은 구독 사용량 기준으로 합니다(`CACHEKEEPER_BASIS=api`면 API 정가). 다른 잣대로 계산된 정책이나 0.5가 API 정가로 계산해 둔 정책은 다음 턴이 끝날 때 다시 계산합니다. 쉬는 구간이 10개보다 적으면 기본값을 쓰고, 어떤 정책도 이득이 없었거나 5분 캐시만 쓰는 경우에는 꺼 둡니다. 재현에서 핑은 빼고 계산합니다. 핑으로 살려 둔 3시간 휴식은 "그때 막은 재구축"과 함께 3시간 휴식으로 셉니다. 그래서 자기가 만든 절약 때문에 스스로 꺼지는 일이 없습니다. Claude Code는 터미널 세션 기록을 마지막 활동 30일 뒤에 지우므로(데스크톱 세션은 보존), 본 쉬는 구간은 숫자만 플러그인 데이터 폴더에 따로 모아 둡니다.

데스크톱 앱에서 실측했습니다([자세히](docs/measurement-2026-09-23.md#keep-alive-live)). 마지막 메시지 55분 뒤와 110분 뒤의 핑이 모두 캐시를 읽었고(5.7만 토큰 Opus 5.5 세션에서 API 정가로 한 번에 $0.014), 112분 뒤에 보낸 메시지는 다시 쓰면 $0.46이었을 것을 $0.015로 처리했습니다.

`cachekeeper events`가 핑 기록과 각 대기가 물러난 이유를 보여 줍니다.

[xinnyu/claude-cache-warm](https://github.com/xinnyu/claude-cache-warm)(`/loop`로 270초마다)과 [meetvaghani12/claude-cache-warmer](https://github.com/meetvaghani12/claude-cache-warmer)도 5분 캐시를 살립니다. 복제 세션에 대해서는 Delitefully의 실측이 있습니다. 살아 있는 세션에 `claude --resume <id> --fork-session -p`를 돌리자 캐시에서 읽은 것은 0이고 54,300토큰을 새로 썼습니다. 시스템 프롬프트에 세션마다 다른 텍스트가 들어 있어서, 복제 세션은 원래 세션이 아니라 자기 캐시를 데웁니다.

cachekeeper가 다른 점:

- **Claude Code 자체 hook.** 핑은 `asyncRewake` `Stop` hook에서 나옵니다. 백그라운드 프로세스, 얼리 액세스 플래그, 예약 작업, 복제 세션이 없습니다. 살아 있는 세션을 그대로 거쳐 그 세션의 캐시를 읽고, 위에 적은 대로 데스크톱 앱에서 실측했습니다.
- **내 기록에서 정하는 정책.** 다른 프로젝트는 고정 기본값이나 사용자가 정한 길이를 씁니다(claude-cache-warm은 대시보드에서 내 기록으로 절약했을 양을 보여 주고, 한도는 사용자가 정합니다). `auto`는 내 휴식을 재현해 최소 크기와 한도를 고르고 매일 다시 고르며, 끝내 돌아오지 않은 세션에 나간 핑도 비용으로 셉니다.
- **구독 사용량 기준.** 위 README 중 핑에 값을 매긴 곳은 모두 API 정가를 씁니다. 정가로는 핑이 대화 전체를 입력 단가의 10분의 1로 읽어서, 1시간 캐시에서 핑 약 20번이 재구축 한 번 값입니다. 외부에서 측정한 구독 사용량([두 가지 잣대](#두-가지-잣대))으로는 읽기가 거의 0이라 핑 한 번이 재구축의 약 1%이고, 그래서 한도를 길게 잡아도 위험이 작습니다. 만든 사람의 기록에서 가장 좋은 한도는 구독 사용량 기준 24시간, API 정가 기준 2시간이었습니다.
- **알아서 물러납니다.** 사용자가 입력하거나, 다른 턴이 끝나거나, 모델 전환이나 `/compact` 뒤, 캐시가 이미 식었을 때, `claude -p` 실행에서는 핑하지 않습니다. 핑을 사용자가 돌아온 것으로 세지도 않습니다.
- **가드, audit과 함께.** 만든 사람의 기록에서는 모델 전환에 든 비용이 쉬었다 와서 캐시가 만료된 비용과 비슷했습니다(사용량의 12.5%와 11.8%). keep-alive는 뒤쪽만 줄일 수 있습니다. 앞쪽은 가드가 맡고, 둘 중 어느 쪽이 더 비싼지는 audit이 알려 줍니다.

하지 않는 것: 핑 줄 숨기기(keepwarm-quiet가 함), 상태 표시줄이나 대시보드의 카운트다운(claude-cache-warm이 함), 컴퓨터를 깨어 있게 붙잡기(santiquiroz의 타이머가 함), 5분 캐시 살리기(마지막 세 프로젝트가 함).

Claude Code 자체 기능도 있습니다. 상태 표시줄에 캐시 만료 시각이 전달되고, `/usage`가 적중률과 마지막 캐시 미스의 원인을 보여 주며, 오래 쉰 큰 세션을 재개하면 요약에서 이어 가기를 제안합니다.

## 요구 사항과 설정

Python 3.8 이상이 필요합니다. 없으면 hook이 아무 말 없이 모든 전환을 통과시킵니다. `PreModelSwitch` hook(keep-alive에는 `asyncRewake` hook도)을 지원하는 Claude Code가 필요합니다. 2.1.280에는 둘 다 있습니다. 체크아웃한 폴더로 바로 시험하려면 `claude --plugin-dir /path/to/cachekeeper`를 쓰세요.

| 변수 | 기본값 | 효과 |
|---|---|---|
| `CACHEKEEPER_MODE` | `ask` | `ask`, `warn`(막지 않고 문구만 표시), `off` |
| `CACHEKEEPER_BASIS` | 캐시를 따름 | `subscription` 또는 `api`: 모든 금액의 [잣대](#두-가지-잣대) |
| `CACHEKEEPER_MIN_USD` | `1.0` | 다시 쓰는 추정 금액이 그 잣대로 이 이상일 때만 묻기 |
| `CACHEKEEPER_MIN_TOKENS` | `100000` | 새 모델 가격을 모를 때 쓰는 기준 |
| `CACHEKEEPER_CONFIRM_SECONDS` | `120` | 다시 요청을 확인으로 인정하는 시간 |
| `CACHEKEEPER_OFFER_SECONDS` | `900` | 전환이 막힌 뒤 다음 메시지를 서브에이전트에 맡기는 유효 시간 |
| `CACHEKEEPER_LANG` | `LANG`에서 | `ko` 또는 `en` |

`~/.claude/settings.json`의 `env` 항목에 넣으면 됩니다.

## 한계

- `prompt_cache_warm`은 지금 모델의 캐시만 가리킵니다. TTL 안에 썼던 모델로 되돌아가면 그 모델의 캐시가 맞을 수 있어서, 실제 재구축은 물어본 것보다 작을 수 있습니다. 재현에서는 29번 물은 것 중 25번이 실제 재구축으로 이어졌습니다.
- 두 재현은 가드와 keep-alive가 했을 일을 모사한 것입니다. 실제로 얼마를 아끼는지는 사용자의 답과 쉬는 습관에 달려 있습니다.
- 구독 사용량 잣대는 외부 실측이라 예고 없이 바뀔 수 있습니다. 읽기 단가는 작지만, 만든 사람 기록은 12.7일 동안 캐시에서 42억 토큰을 읽었습니다. 80% 구간(입력 단가의 0~0.5%)에 따라 읽기가 구독 사용량의 0%에서 12%를 차지합니다. 1시간 캐시 쓰기가 입력 단가보다 비싸게 세어지지 않는다는 것은 실측되지 않았습니다. 정가처럼 2배로 센다면 재구축이 더 무거워지고, 가드와 keep-alive는 여기 나온 것보다 더 아낍니다.
- keep-alive 핑은 대화에 보이는 짧은 턴이고, 다른 요청처럼 사용량에 들어갑니다.
- keep-alive는 컴퓨터가 깨어 있고 세션이 열려 있을 때만 동작합니다. 핑은 그 세션이 직접 보내는 요청이기 때문입니다. 절전으로 한 시간이 지나 버렸으면 재구축 비용을 치르는 대신 물러납니다.
- 가드는 Claude Code가 `PreModelSwitch`로 넘기는 전환만 봅니다. effort 변경도 대부분의 모델에서 캐시를 무효화합니다(Opus 5.5와 Fable 5.1은 예외). 이 경우는 캐시가 살아 있을 때 Claude Code가 직접 확인을 묻습니다.
